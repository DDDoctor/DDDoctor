# 故障排查

## 0. 先看日志

程序目录下的 `multiview.log` 会记录：

```
程序启动 / VLC 运行库就绪 / 主窗口构建完成 / 进入事件循环   ← 启动时间线
通道 N 连接失败，X 秒后第 Y/Z 次重连                      ← 断流重连
关闭：后台收尾完成，耗时 X.XXs                            ← 关闭耗时
```

启动时间线能区分"启动慢"和"运行卡"；重连记录能看出是哪几路一直连不上。

---

## 1. 多路画面里有黑屏

**先判断是"程序问题"还是"设备/地址问题"**：

### 1.1 最常见的真因：多路用了同一个流地址

用同一台设备反复拉**同一路码流**会触发设备的并发连接数上限，超出的那几路
连接被拒 → 画面黑屏 / 一直"重连中"。日志里会看到 `通道 N 连接失败`。

**实测案例**（车载 NVR，11 路全部填了同一个地址）：

| 配置 | 结果 |
| --- | --- |
| 11 路全部 `.../Channels/1` | **8 路在线、3 路连接失败（黑屏）** |
| 抓到的日志 | `通道 8 / 9 / 11 连接失败，3 秒后第 1 次重连` |

**解决**：每一路填**各自的通道地址**。

### 1.2 怎么找出设备真正支持的地址

```powershell
# 试探常见的通道号写法
.\.venv\Scripts\python.exe tools\url_probe.py --host 192.168.1.10

# 或只测几个指定地址
.\.venv\Scripts\python.exe tools\url_probe.py --urls "rtsp://ip:554/Streaming/Channels/1,rtsp://ip:554/Streaming/Channels/2"
```

实测某台车载 NVR 的结果（供参考）：

```
✅ rtsp://192.168.1.10:554/Streaming/Channels/1     1280x720   ← 通道1 主码流
✅ rtsp://192.168.1.10:554/Streaming/Channels/2     704x576    ← 通道2（D1）
✅ rtsp://192.168.1.10:554/Streaming/Channels/101   1280x720   ← 等于通道1
❌ rtsp://192.168.1.10:554/Streaming/Channels/3     Playing 但无画面
❌ .../Channels/201、/4、/5、/6                     Ended
```

**结论**：这台设备实际只有通道 1、2 有流。要接 11 路就得换设备，
或者确认设备端其它通道是否已接入摄像头 / 是否用了别的 URL 格式。

### 1.3 逐个通道检查程序侧状态

```powershell
# 在进程内逐路打印：状态、有无视频输出、VLC 绑定的窗口句柄是否还有效
.\.venv\Scripts\python.exe tools\cells_probe.py --n 11 --url "rtsp://..."
```

若某路显示 `无视频输出` 或 `VLC 绑定的句柄已失效`，那才是程序问题。

## 2. 没有声音

**只有没勾「静音」的通道才会出声**，多路同时出声会互相盖住。

1. 看画面标题栏的小喇叭：🔊 绿色 = 在出声，🔇 灰色 = 静音；
2. 选中某路 → 点工具栏 **🎧 仅此路出声**；
3. 确认系统音量和默认播放设备；
4. 确认**流本身有音轨**：

```powershell
.\.venv\Scripts\python.exe tools\audio_probe.py --url "rtsp://..."
# 需要看 VLC 的详细日志时：
.\.venv\Scripts\python.exe tools\audio_verbose.py --url "rtsp://..."
```

`audio_verbose.py` 会打印关键几行，例如正常时应出现：

```
main audio output debug: using audio output module "mmdevice"
mmdevice audio output debug: simple volume changed: 0.512000, muting disabled
live555 demux debug: RTP subsession 'audio/MPEG4-GENERIC'
main decoder debug: using audio decoder module "faad"
```

如果 `音轨数量` 为 0，说明**摄像头/NVR 主码流是纯视频**，
需要在设备端打开麦克风 / 音频编码。

---

## 3. 界面卡死 / 点不动

v1.0.4 起已把**所有**会抢 libvlc input 锁的调用移出 UI 线程（见 `CHANGELOG.md`）。
如果仍遇到卡死，用监控脚本自动抓现场：

```powershell
# 另开一个窗口运行，然后正常操作程序，卡死时会自动抓线程堆栈
.\.venv\Scripts\python.exe tools\monitor.py --duration 1800
```

卡死瞬间会写入 `monitor_report.txt`：所有线程的 Python 堆栈（精确到源码行）、
CPU / 内存 / 线程数时间线、现场截图、程序日志尾部。

---

## 4. 画面花屏 / 绿屏 / 马赛克

显卡驱动兼容性问题。把「配置 → 播放设置 → 硬件解码」改成
**关闭（软件解码）** 再试。

---

## 5. 多路卡顿

* 开启硬件解码（默认「自动」）。实测 6 路 720P：硬解 85% 单核 vs 软解 129%；
* 内存比 CPU 更容易先成为瓶颈：**每路约 200–250 MB**，
  6 路实测 1.48 GB，18 路约需 4.4 GB；
* 网络带宽：单路 1080P H.264 约 2–8 Mbps，18 路需要 40–150 Mbps 稳定内网；
* 摄像机建议用**子码流**（分辨率低、码率小）。

程序右下角状态栏会实时显示**当前进程内存占用**，可直接观察。

---

## 6. 录制相关

| 现象 | 说明 |
| --- | --- |
| 开始/停止录制时画面卡一下 | sout 机制的必然重连，约 1 秒，其它通道不受影响 |
| 录制中截图失败 | sout 模式下 VLC 不注册可截图的 vout，先停录制再截 |
| 找不到录制文件 | 「文件 → 打开录制目录」；默认在**程序目录下的 `recordings\`** |
| 换版本后还写进旧目录 | v1.0.5 已改为相对路径并自动迁移旧配置 |

直播流建议用 **TS**（默认，最稳）；MKV 容错性好；**MP4 不适合直播流**
（程序异常退出时文件会损坏）。

---

## 7. 双击不全屏 / 鼠标点不动

* v1.0.2 起双击 = **单画面全屏**（隐藏菜单栏/工具栏/状态栏），再次双击或 `Esc` 还原；
* 某些显卡驱动下 VLC 的视频窗口会吞掉鼠标消息，
  此时**双击标题栏**或点工具栏「放大/还原」按钮同样有效；
* 也可用工具栏的「当前通道」下拉框选择通道。
