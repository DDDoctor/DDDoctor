# 架构说明

## 1. 总体结构

```
main.py                    入口：装 VLC 运行库 → 建 Qt 应用 → 建主窗口
app/
├─ constants.py            常量：通道上限、状态机、颜色、文案
├─ paths.py                路径解析（源码运行 / PyInstaller 打包后）
├─ config.py               配置数据模型 + JSON 读写 + 目录迁移
├─ vlc_runtime.py          定位并接入 libvlc（内置 / 系统安装 / 环境变量）
├─ dispatch.py             ★ 后台线程池：隔离所有阻塞的 libvlc 调用
├─ player.py               ★ 播放内核：libvlc 封装、事件、状态机、重连、录制
├─ wall.py                 自动网格布局计算与摆放
├─ cell.py                 单个画面单元（标题栏 + 画面区 + 状态占位层）
├─ settings_dialog.py      配置弹窗
├─ sysinfo.py              进程内存查询
└─ main_window.py          主窗口：工具栏、菜单、状态栏、各种操作
```

## 2. 核心技术决策

### 2.1 为什么用 libvlc 而不是 QtMultimedia

libvlc 对 RTSP / RTMP / HLS / 组播的支持最完善，硬解、丢包恢复、协议兼容性
都远好于 Qt 自带后端。代价是要自己处理 libvlc 的线程模型（见下）。

### 2.2 渲染方式

`media_player.set_hwnd(窗口句柄)` 把 VLC 的视频输出嵌到 Qt 部件的 HWND 上。
这是 Windows 下最稳、性能最好的内嵌方式。

**注意**：VLC 会在给定 HWND 内创建一个子窗口，它的 z 序高于同级的非原生
Qt 控件。因此"未播放"提示层（`cell.py` 的 `_Placeholder`）必须显式声明
`WA_NativeWindow` 才能盖在视频上面。

### 2.3 线程模型（本项目最关键的部分）

libvlc 3.x 里有一大批**同步阻塞**的接口：

| 接口 | 为什么阻塞 |
| --- | --- |
| `stop()` / `set_media()` / `release()` | 要等输入线程结束 |
| `play()` | 起流过程可能等待 |
| `video_set_aspect_ratio()` / `video_set_scale()` | 内部先 `libvlc_get_input_thread()` |
| `audio_set_volume()` / `audio_set_mute()` | 同上 |
| `video_take_snapshot()` | 同上 |

后四个要抢 libvlc 的 **input 锁**。只要后台有任意一路的 `stop()` 在跑
（NVR 断流时单次可达 3 秒），**在 UI 线程调用这些方法就会排队等锁** ——
这就是"点一下配置就卡死十几秒"的根因。

**解决办法**（`app/dispatch.py`）：

* 每个工作线程是一个 **FIFO 队列**，同一通道的操作按提交顺序串行执行；
* 用 4 个线程轮转（`index % 4`），保证某一路卡住不拖累其它通道；
* 线程用普通 Python **守护线程 + `queue.Queue`**，不用 `QThread`
  —— QThread 对象在解释器退出时被析构、而线程仍在运行会让 Qt `qFatal`，
  导致进程 9 秒退不掉并留下僵尸。

### 2.4 事件回流

libvlc 的事件回调运行在 VLC 自己的线程里。回调只做一件事：`emit` 一个
Qt 信号，真正的状态机与界面更新全部在主线程执行。

```
VLC 线程 ──emit──▶ Qt 队列 ──▶ 主线程 _on_vlc_state() ──▶ 状态机/界面
```

### 2.5 状态机与自动重连

```
IDLE ──play──▶ CONNECTING ──▶ BUFFERING ──▶ PLAYING
                   │              │            │
                   └── 超时/错误 ──┴── 断流 ───┘
                              ▼
                        RECONNECTING ──按 1x/2x/4x… 退避重连（最长 60s）
                              ▼（超过最大重试次数）
                          OFFLINE
```

* **看门狗**：起流后 `connect_timeout` 秒仍未播放则判为失败；
  处于缓冲中会不断延后看门狗，但总等待不超过 `connect_timeout × 3`。
* **陈旧事件过滤**：每次起流都是先 `stop()` 再 `play()`，会收到一条陈旧的
  `stopped` 事件，处于 CONNECTING 时忽略它，避免无谓重连。

### 2.6 网格布局算法

按「窗口真实宽高比 + 通道数」枚举所有 (行,列) 组合，用**黑边浪费面积 +
空格浪费面积**打分，取最优；末行会等分拉伸铺满，不留空白格。

```
1→1×1   2→1×2   3→2×2   4→2×2   5~6→2×3
7~9→3×3  10~12→3×4  13~16→4×4  17~18→4×5
```

### 2.7 录制

libvlc 3.x **没有**录制开关 API，只能用 sout 管线：

```
#duplicate{dst=display,dst=std{access=file,mux=ts,dst=<文件路径>}}
```

由此有两个必然限制（界面里已给出提示）：
1. 开始/停止录制会让该通道**重新连接一次**（约 1 秒）；
2. **正在录制的通道无法截图**（sout 模式下 VLC 不注册可截图的 vout）。

### 2.8 路径与配置

* 配置 / 日志 / 截图 / 录制默认都放在**程序所在目录**；
  该目录不可写时退回 `%APPDATA%\MultiView`。
* 截图 / 录制目录在配置里存**相对路径**（`snapshots` / `recordings`），
  所以换版本、挪目录都会自动跟随；也支持用户指定绝对路径。
